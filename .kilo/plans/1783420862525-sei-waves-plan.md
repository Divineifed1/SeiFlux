# SeiFlux Waves — Implementation Plan

## Goal
Add a recurring monthly 8-day wave event to SeiFlux. During waves: contributions are incentivized, applications/PRs flow into wave-approved projects, and maintainers merge. Outside waves: normal contribution continues but is not wave-incentivized. Incomplete contributions auto-rollover unless a maintainer explicitly closes them.

## Key Clarifications
- Wave cadence: every month.
- Wave length: flat 8 days (no split phases).
- Project submission timing: anytime; no first-come-first-serve window.
- Wave scope: all existing/live projects are wave-eligible by default.
- Post-wave rule: unresolved applications/PRs roll over to the next wave automatically, maintainers can close instead.

## New Data Model

### `Wave`
| Field | Type | Notes |
|-------|------|-------|
| `id` | string | UUID |
| `name` | string | e.g., `Wave #1 - July 2025` |
| `startsAt` | Date | wave start |
| `endsAt` | Date | wave end = startsAt + 8 days |
| `status` | `upcoming/active/completed` | derived but stored for queries |
| `createdAt` | Date | |

### `Application` extension
- Add `waveId?: string` to link an application to a specific wave.
- Add `rolledOverAt?: Date` when copied to next wave.
- Add `closedAt?: Date` when a maintainer closes instead of rolling over.

### Backend routes
- `GET /waves` — list waves (newest first).
- `GET /waves/current` — current active wave or 404.
- `POST /waves` — admin-only: create next wave (auto compute 8-day window).
- `POST /waves/:id/close` — admin/maintainer action: triggers rollover logic for that wave.

### Frontend
- Wave banner/schedule on public and dashboard pages showing current wave dates.
- Wave-aware filtering in Discover/issues: `status=wave-approved` implied for all projects but UI surfaces wave timing.
- Maintainer tools: view wave-bound applications, mark as closed or let roll over.

## Behavior Details
1. **Active wave check**: lightweight env-derived + DB fallback to determine if today is inside the current wave.
2. **Incentives**: tracked counts (applications merged during wave) shown on project cards during active wave only.
3. **Rollover**: when a wave closes, all `pending/review` applications without `closedAt` are copied to the next wave and original `rolledOverAt` is stamped. Maintainer action required to opt out.
4. **Contributions outside waves**: still fully supported; Applications can be created without `waveId` (backwards-compatible).

## Migration / Compatibility
- `waveId` and `rolledOverAt` are nullable on Application so old data remains valid.
- Existing `opportunities` rename already done; Issue/Project/Application types remain same.

## Risks
- Rollover needs idempotency; dedup by (originalApplicationId + targetWaveId).
- Maintainers may expect manual opt-in per project; current design defaults to all projects participating to reduce friction.
